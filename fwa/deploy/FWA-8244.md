# fwa.wei onchain page (ERC-8244 / ERC-5219 / ERC-4804)

An onchain HTML front end for Fake World Assets: the FWA core contract
`0xB276F62DB0ce8CA2Ca5bc522695bE604521eAc1c` on mainnet, the FWA token
`0xa0Df17B5aC76ABaBA36E1450E2cbCd18A620C845` and its buyback pipeline, and the
separate TokenWorks retroactive buyback contract
`0xabc98D86eA62919399c4211251890308Ce37A6BF`.

## Where the page came from

The hosted site is `fwa.eth`, four documents pinned on IPFS behind an ENS name:
`index.html`, `impact.html`, `buybacks.html`, `fwair.html`, plus one stylesheet,
three scripts and three images. This is that application as one file, with the
changes an onchain page needs and no others.

**Four documents became four routes.** A gateway serves this contract's single
document from every path and never sees a fragment, so the route lives in the
client: `#/impact`, `#/buybacks`, `#/fwair`, and `#/home` for the hub, with a
same-page anchor written after the route as `#/home/collections`. Each route
runs its own page's script the first time it is shown, so opening the hub does
not start three sets of chain queries. Every page's own header, main and footer
are kept intact rather than merged, so each route is the document it was.

**Nothing is fetched to render.** The stylesheet and the three scripts are
inline. The logo is one CSS custom property painted behind
twelve `<img>` elements that all point at a 70-byte transparent pixel, so the
PNG is in the page once rather than twelve times.

The mark itself is redrawn: the hosted site's reads **FWA.eth**, and a page
served from `fwa.wei` cannot carry a picture of a different name. The source is
`dapp/assets/fwa-wei-logo.png`; the embedded copy is that file trimmed to its
ink, resampled in premultiplied alpha to 152 px tall (twice its largest
on-screen size) and quantised to a 256-colour palette, which takes it from
2.26 MB to **13,433 bytes**. `.wei` is a wider word than `.eth`, so the mark is
2.68:1 where the old one was 2.35:1 — it is therefore sized by letter height
rather than by the stylesheet's box widths, which keeps the letters exactly the
size they were and lets the mark be wider instead of smaller. The favicons are data URIs. `ipfs://` is still
resolved through public gateways for **one** thing — the picture of the NFT
currently on top — because that URI is chosen by whoever minted the token and
is not ours to store.

**The name changed, so the copy changed with it.** Every `fwa.eth` in the page
now reads `fwa.wei`, and "Published on IPFS. Resolved through ENS." now reads
"Published on Ethereum. Resolved through WNS." A page that calls itself by a
name it is not served under sends its own readers somewhere else. Each footer
links [ERC-8244](https://eip.tools/eip/8244) and, once the page knows which
contract served it, names that contract.

## What was fixed on the way in

Two things the hosted site gets wrong, both verifiable against the chain:

**"FWA TO RESERVE" was blank on every load.** `retroData` sampled a handful of
transaction receipts to guess which address the bought FWA repeatedly lands on,
and skipped any transfer landing on an address it already knew — and the program
contract is one of those. It therefore found no destination on this program and
left the figure empty. The indexed ERC-20 transfers on the program address hold
the answer outright: 310 transfers in, 310 back out, 35.65M FWA, matching the
310 one-ETH slices the balance already implies. It is measured now, and the
receipt heuristic stays as the fallback.

**The execution feed showed a couple of dozen entries for 310 buys**, because it
listed direct transactions to the program contract rather than the executions.
It follows the same transfers now, and each row says what its slice bought.

## The reader's Ethereum

There is no backend and no wallet: every number is read from Ethereum by the
browser showing the page. Which Ethereum is therefore the one setting worth
having, and it is the reader's — a control in the corner of every route lists
the endpoints, tests each one live, says whether it serves state only or event
logs too, and lets the reader untick any of them or add their own. Precedence is
`?rpc=` in the URL, then what they saved, then the public list.

The public list is seven endpoints that each answered `eth_chainId`,
`eth_blockNumber`, `eth_call` and `eth_getBlockByNumber` on eight consecutive
rounds from a browser origin. **Two that worked were left out anyway:**
Blockscout and Flashbots both answer `eth_getLogs` and both silently return a
short array on a range that holds more — over 5,000 blocks of FWA core logs,
where Tenderly, dRPC and MEV Blocker all returned the same 8,242 entries,
Blockscout returned exactly 1,000 and Flashbots returned 616, with no error to
notice. A total summed from a truncated log set is wrong in a way nobody can
see, which is worse than a number that fails to load.

## Build

Everything below is run from this directory. `forge` comes from Foundry; the
jsdom tests need `npm i` at the repo root.

```
node ../scripts/chunk.mjs fwa       # out/Fwa8244.chunk1..9.creation.txt
forge test --match-path test/Fwa8244.t.sol
node test/dapp/fwa.routes.mjs       # routing, the RPC control, the page offline
node test/dapp/fwa.live.mjs         # the real page against mainnet in a browser
node ../scripts/serve.mjs fwa       # localhost, real reads, real chain
node ../scripts/verify.mjs fwa      # chunks, html() and every route, against mainnet
```

The chunker writes into `out/`, which is also Foundry's artifact directory, so
run it again after any `forge clean`.

`testServesTheRepoPage` deploys the chunks and asserts `html()` is
`dapp/page.html` byte for byte, so a stale chunk set fails the suite rather than
reaching a deploy.

## Deploy order

1. Deploy each chunk initcode from `out/`. Each returns `STOP || slice` as
   runtime bytecode; nothing else is in them.
2. Deploy `Fwa8244(steward, address(0), chunks, keccak256(page))` — constructor
   args appended to the creation code. `previous` is zero for the first version.
   The constructor reassembles the page from the chunks it was given and reverts
   unless it hashes to the commitment, so a reordered or missing chunk cannot
   deploy.
3. Read it back: `cast call <addr> "html()(string)" > fwa.html`.

Browse at `https://<addr>.w4eth.io/` (ERC-8244) or
`https://<addr>.1.w3link.io/` (ERC-4804, through the ERC-5219 `request()`),
then point `fwa.wei` at the contract for `https://fwa.wei.limo/`.

## Stewardship

Initial steward: `0x1C0Aa8cCD568d90d61659F060D1bFb1e6f855A20`.

The steward is **not** immutable: keys rotate and signer sets migrate, and
freezing the role into the bytecode would mean any such change ends the lineage.
`transferStewardship` / `acceptStewardship` move it in two steps;
`renounceStewardship` freezes it deliberately and clears any standing offer.

What is *not* relaxed: `PREVIOUS` and `successor` are write-once and checked
before they are set, so the chain a reader walks cannot be restated by a
steward, new or old. `deployNext` creates the successor with CREATE2 from this
contract, so its constructor sees `msg.sender == address(this)` and nothing
outside that function can produce a contract naming this one as its parent.

`html()` never forwards. The successor is a claim about lineage, not a redirect:
this address serves its own chunks forever, and the page merely puts a link in
its footer when `latest()` is not itself.

## Growing the page

Nine chunks hold 221,184 bytes; the page is 214,280, so there are **6,904
bytes** of headroom at this chunk count. Past that the count — and therefore the
address — changes, which means a new wrapper deployed as a successor, not an
edit.
